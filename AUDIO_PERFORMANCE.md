Independent branch `fix/audio-focus-performance-206`, based on `d4e48f239fec17935e8ba2747b275be930d00fea` (the installed 1.0.205 preview). No main merge. Application ID, HOME/Accessibility, original AndroidManifest, themes, lens geometry, app ordering, backgrounds and existing sources remain unchanged. Automatic updates remain frozen. This build explicitly increments versionName/versionCode to **1.0.206 / 206**.

## Audio findings and limits

The original TV and radio code did **not** contain an explicit sub-unity volume assignment; the original defaults are normally 1.0. A universal volume defect on the physical MECOOL/HDMI output therefore cannot honestly be attributed solely to an existing `setVolume(0.2)` or similar line.

Concrete defects found: Quran radio used legacy focus, ignored duck/gain events, stopped permanently on transient loss, ignored focus-request denial, and was not coordinated with the in-app TV player. Selecting another station from the prayer page could prepare two consecutive players because both `choose()` and the click handler called play. Reopening the station page also launched redundant source refreshes. An own-package adhan is deliberately excluded from external MediaSession restoration, so in-app players need explicit restoration of their own.

`PlaybackAudio` now gives one in-app media owner priority. Both media backends use `USAGE_MEDIA`, explicit unity gain, one focus request, and pause-on-duck semantics instead of applying a persistent attenuation multiplier. A transient loss pauses; gain restores **only the still-requested current owner** at 1.0. Permanent loss, user pause, replacement and close prevent accidental restart. Adhan explicitly suspends this owner and releases its own focus before restoring it; external MediaSession restoration keeps its original guards. No system volume, alarm volume, equalizer, loudness enhancer or gain above unity is changed.

Radio now uses the existing Media3 dependency as an audio-only player with a bounded 2MiB buffer and speech attributes; station URLs/preferences/fallbacks are retained. Replacing TV with radio stops TV decoding; replacing radio releases its player. Closing its prayer player page/dialog or leaving the owning activity stops radio. TV window close and lifecycle dismissal release its decoder, focus, requests and timers. During adhan, media loading/decoding is stopped while retaining the requested station identity; restoration reconnects at the current/default position so a four-minute paused radio socket or expired HLS window is not reused. Short notification interruptions only pause. Noisy-output events cancel resume intent. Pending/denied focus never starts audible media without a grant.

Eight-second real source samples were decoded separately with FFmpeg at unchanged gain. The saved raw evidence is `tests/audio-source-samples.json`. At sampling time Cairo Quran was approximately -26.9 dBFS RMS / -8.9 dBFS peak; MBC Bollywood -28.8 / -11.3; MBC3 USA -26.6 / -7.0; NHK -25.8 / -8.5. These are short programme-dependent **source** samples, not LUFS normalization, listening tests, physical speaker loudness or a comparison with another TV app. The sampled tracks were stereo, so these samples do not establish a multichannel downmix defect. The Mishary fallback returned HTTP 500 in that sample; it is not misreported as verified audio and its existing URL is retained.

If a feed remains quieter at unity, an opt-in per-player loudness processor with peak limiting and conservative gain is a safe next option after longer loudness measurements; a blanket gain increase risks clipping louder programmes. No such unrequested automatic boost is enabled here. MECOOL Android audio/Dolby/HDMI processing still needs testing on the actual device; this environment has no physical TV output or microphone measurement.

## Concrete UI work removed

The shared animated app-focus overlay previously occupied MATCH_PARENT bounds. It now keeps the same root-space spring/geometry/glow but bounds its visual node to the actual frame, reducing whole-window damage during every arrow animation. Settings also skips restyling unchanged sidebar rows. Neither change alters focus order or animation speed.

- `Glyphs.get()` previously rasterized a fresh bitmap on every call, including every sidebar/control focus style update. A bounded 4MiB shared glyph cache now reuses identical pixels; no shared bitmap is recycled while views hold it.
- Night Scenes' cached software frame occupied another full ARGB image (31.6MiB at 3840×2160) and rendered the clock/scene into it on the main thread. Android 10+ hardware canvases now record the same drawing commands in a RenderNode. Software/older-device fallback remains, and the previous complete scene stays visible while loading. Bitmap ownership is retired safely while GPU/worker references exist.
- Dialog assets and per-row PNG backgrounds were decoded on the main thread on window creation/list binding. `UiArtwork` samples to actual display needs, decodes on background workers, prewarms common art, shares pixels through a bounded cache, and uses independent drawables. Layouts, artwork files, colors and animation durations are retained.
- Prayer dialog recomputed the monthly JSON, timezone, next seven days of events, date strings and five glass backgrounds every second. It now caches calendar/event snapshots and recomputes on data/day/next-prayer changes; only the visible countdown continues at 1Hz. Hidden subpages stop the pulse; leaving the launcher disposes the dialog.
- Night dock selection wrote SharedPreferences at every focus hop. Persistence is coalesced without delaying focus, then flushed on pause. The app-logo cache is bounded at 8MiB.
- Remote navigation no longer resolves an input device/Unicode character through the keyboard-search path for known D-pad/Back/Menu/Enter keys. Keyboard search remains available for actual typed characters.
- Live catalogue audit JSON/directory setup moved off the UI constructor. Audit data is shared immutably, and formatted row status text is bounded/cached with invalidation on playback success/failure.

## Actual verification protocol

The Actions job builds the exact installed-version baseline and candidate from separate source trees, injects the **same test profiler only**, and runs them sequentially on the same Android 14 emulator at 1080p and 4K. Clean app data, the same recorded real prayer/channel fixtures, disabled network in the performance phase, enabled animations and the same key script are used. Both cold and repeated window opens are measured. FrameMetrics, main-thread CPU, PSS/heaps, disk violations and a 5ms main-thread stack sampler are saved, with atrace captures and dumpsys/logcat. JIT/cache/host load still cause variance; raw per-stage numbers, including regressions, are reported instead of claiming a universal speedup. See the release's generated `performance-comparison.md` and raw JSON, not an invented before/after percentage.

Audio instrumentation uses real MBC Bollywood, MBC3 USA, NHK and Cairo Quran streams, playback positions, audio formats/session IDs, explicit player-volume checks and actual separate-test-UID notification focus. It waits for the entire unmodified 246-second Ali Mulla adhan recording to finish naturally while radio is interrupted, then checks unity restoration. Additional real-adhan stop and user-pause cases check TV restoration and cancellation. Radio/TV replacement, repeated close, prayer-page Back and unchanged system volume are checked. Test helpers/probe services exist only in the separate test APK, not the delivered launcher. Original parser/prayer/match/news tests and full real-broadcast/remote/search/favorite/fullscreen/Back regressions remain part of the build.

Only the final successful Actions run is evidence that these checks passed. The report deliberately distinguishes emulator playback/routing checks from audible physical-device validation. APK is development-signed and may not update over a differently signed installed copy.
